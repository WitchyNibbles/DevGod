# Agentic Frontend Inspiration Sources

This document records the upgraded public/free inspiration and implementation stack that autonomous `devgod` frontend agents should use before implementing a substantive redesign, especially for immersive, motion-heavy, game-like product surfaces.

## Decision

The strongest public/free source stack for originality-focused autonomous frontend work in `devgod` is now:

1. `Awwwards`
2. `Godly`
3. `Siteinspire`

`Lapa Ninja` stays in the workflow as a runner-up supplement for full-page landing density and section rhythm, but it should no longer be treated as part of the default top-three stack for broad redesign quality.

Official implementation guidance should be paired with those inspiration sources when motion-heavy or media-heavy work is requested:

- `Motion` for React: [motion.dev/docs/react](https://motion.dev/docs/react)
- `Rive`: [rive.app/docs/runtimes](https://rive.app/docs/runtimes) and [state-machine overview](https://rive.app/docs/editor/state-machine/state-machine)
- `GSAP ScrollTrigger`: [gsap.com/docs/v3/Plugins/ScrollTrigger/](https://gsap.com/docs/v3/Plugins/ScrollTrigger/)
- `three.js` scene fundamentals: [threejs.org/manual/en/creating-a-scene.html](https://threejs.org/manual/en/creating-a-scene.html)

## Why the first stack was not enough

The original shipped stack over-weighted structural browsing and full-page coverage. That improved sourcing discipline, but it still allowed agents to average references into a competent themed dashboard instead of an authored, memorable interface.

The failure mode was:

- safe shell first
- tasteful styling second
- no signature move
- weak asset strategy
- decorative scene props standing in for art direction

So the new stack is optimized less for breadth and more for:

- ambition ceiling
- curation strength
- anti-generic taste calibration
- structurally useful retrieval

## Evaluation criteria

- public and free browsing
- high curation quality
- enough structure for agentic retrieval
- strong resistance to median dashboard output
- usefulness for composition, motion, typography, and authorship decisions
- repeatable value inside an autonomous workflow

## Top 3

### 1. Awwwards

URL: [awwwards.com/websites](https://www.awwwards.com/websites/)

Why it is now first:

- It exposes the highest visible ambition ceiling in the stack.
- It is the best source for motion, interaction, composition risk, and high-concept web direction.
- Its public browse surface exposes categories, tags, technologies, fonts, and colors, which keeps it usable for agents rather than only for humans.

Best use in `devgod`:

- finding a signature move
- calibrating ambition
- sourcing motion and interaction references
- escaping safe app-shell defaults

Supporting source:

- browse surface and taxonomy on [Awwwards websites](https://www.awwwards.com/websites/)
- evaluation weighting on [Awwwards evaluation](https://www.awwwards.com/about-evaluation/)

### 2. Godly

URL: [godly.website](https://godly.website/)

Why it moved into the top three:

- The public surface is more selective and better for taste calibration than large broad galleries.
- For autonomous work, this matters because the main failure mode is not lack of examples. It is averaging too many examples into generic output.
- Godly is better at answering "does this feel authored?" than "how many similar pages exist?"

Best use in `devgod`:

- taste calibration
- quality-over-quantity sourcing
- rejecting average-looking product surfaces

Supporting source:

- public site and curation framing on [Godly](https://godly.website/)

### 3. Siteinspire

URL: [siteinspire.com](https://www.siteinspire.com/)

Why it remains in the top three:

- It is still the best structural retrieval source in the stack.
- The public surface exposes `Categories`, `Styles`, `Types`, `Subjects`, and `Platforms`, which makes it especially useful for layout and category matching.
- It is less useful for ambition than Awwwards and less useful for taste calibration than Godly, but it is still the best structural map.

Best use in `devgod`:

- layout structure
- subject and platform matching
- translating product type into reference filters

Supporting source:

- public browse taxonomy on [Siteinspire](https://www.siteinspire.com/)

## Runner-up

### Lapa Ninja

URL: [lapa.ninja](https://www.lapa.ninja/)

Why it stays in the workflow:

- It is strong for full-page screenshots, landing density, and section sequencing.
- It is useful after the concept is already chosen and the agent needs concrete long-page composition help.

Why it is no longer top three:

- It is better for coverage than for authorship.
- Left as a default source, it can push the workflow back toward polished-but-familiar product layouts.

## Exclusion

### Land-book

URL: [land-book.com](https://land-book.com/)

Why it remains excluded:

- The free plan limits access to categories, sections, and filter/search results.
- Under the public/free autonomous workflow constraint, that makes it weaker than the shipped stack.

## Workflow implications

Autonomous frontend redesign tasks should now:

1. collect at least 6 references from at least 3 sources
2. include at least 1 `Awwwards` reference for ambition
3. include at least 1 `Godly` reference for taste calibration
4. include at least 1 `Siteinspire` reference for structural relevance
5. include at least 1 non-web reference such as poster, editorial, album art, game UI, or packaging
6. name a `signature move` before implementation begins
7. reject the direction if the screen would still look generic with the text blurred
8. use `Lapa Ninja` when full-page landing rhythm is the actual problem, not as a default starting point

## Core diagnosis

The main missing ingredient in the earlier workflow was not "better CSS taste." It was authorship pressure.

Strong UI systems do not just say:

- use references
- make variants
- critique screenshots

They also force the agent to answer:

- what is the memorable move?
- what source is pushing ambition?
- what source is calibrating taste?
- what keeps this from collapsing into a safe app dashboard?
- what motion system makes this feel alive?
- what media system makes this visually rich without becoming janky?
- what is the lightest implementation stack that can still deliver the concept?

That is the problem this upgraded stack is meant to solve.

## Why implementation guidance is now part of the workflow

The earlier originality upgrade improved authorship pressure, but it still left a gap: an agent could choose bold references and then implement them with low-energy fades, toy decoration, or a stack mismatch.

The modern immersive workflow now pairs taste sources with official implementation references because:

- `Awwwards` still clarifies the ambition ceiling and balances `Design`, `Usability`, `Creativity`, and `Content` in a public evaluation system.
- `Motion` provides a practical React-native path for smooth layout, state, scroll, and gesture choreography with reduced-motion support and browser-native performance primitives.
- `Rive` adds an authored interaction layer that is closer to polished game UI or product art than hand-built CSS decoration, while still shipping to web runtimes with explicit renderer and size guidance.
- `GSAP ScrollTrigger` is better when the concept depends on orchestrated timelines or pinned scroll narratives rather than ordinary component transitions.
- `three.js` should be reserved for concepts that truly need spatial depth, camera movement, or interactive 3D rather than being used as decorative overkill.

In other words, `devgod` now treats immersive frontend work as a combined art-direction and implementation-fit problem, not just a styling problem.

## Why the latest cinematic remake still failed

The latest `hexchange` remake did solve one old problem: it no longer looked like the same left-rail occult dashboard family.

But it still failed the impressiveness bar for three workflow reasons:

- the artistic medium was still too thin, with identity carried mostly by typography, gradients, clipped panels, and CSS atmosphere instead of truly authored assets or interactive motion
- the wow factor was vague, so the agent produced a premium mood rather than a memorable visual event
- functionality preservation was not part of the same art-direction contract, so route-critical actions could become harder to find even while the page looked more curated

That means the next workflow upgrade must pressure three things together, not separately:

- artistic ceiling
- asset craftsmanship
- critical-control discoverability

## Additional workflow evidence

Three newer workflow signals reinforce this direction:

- Vercel’s v0 guidance explicitly recommends screenshots and even rough sketches as design guides, because spatial and aesthetic intent are hard to derive from text alone.
- Replit Agent 4 emphasizes an infinite design canvas, multiple UI variants, and direct in-context exploration instead of a one-shot implementation jump.
- Lovable’s visual edits model shows why targeted visual iteration matters: fast edits to layout, text, colors, fonts, and images help teams correct taste and control-discoverability issues without rewriting the whole surface.

Together, these sources suggest that `devgod` still needs more than stronger prompts. It needs stronger contracts around what kind of visual artifact must exist before code is considered “impressive.”

## New diagnosis: legacy anchoring

The latest `hexchange` failures exposed a separate problem from generic taste: the agent kept treating the current frontend as a scaffold to improve instead of as legacy material that could be discarded. That creates a predictable failure pattern:

- old section order survives under new styling
- old shell silhouette survives under new motion or atmosphere
- old and new motifs get layered together instead of replaced
- the result feels like an alternate version of the same product, not a new concept family

This maps to classic design-fixation evidence: examples and prior artifacts narrow novelty unless the workflow explicitly forces divergence. It also matches stronger modern UI-agent workflows that rely on variants, design canvases, screenshot-led iteration, and reversible exploration instead of editing the existing surface in place.

## Archon audit delta for Codex

The comparable `archon` control surface does one Codex/Claude-facing thing that `devgod` had not stated clearly enough in the shipped frontend workflow:

- it exposes a single frontend entrypoint skill (`archon-frontend`) instead of expecting the agent to decide ad hoc among several overlapping frontend guidance files
- it gates the frontend skill cluster behind a real UI surface so backend or infra tasks do not pay the routing overhead
- it documents the hub-to-detail skill chain in the role surface, which makes agent behavior easier to predict and verify

`devgod` already exceeds `archon` on the originality and media-first contract. The missing piece was the routing architecture. The Codex-native adaptation for this repo is therefore:

1. keep `devgod-ui-art-direction` as the richer contract
2. explicitly use it as the frontend entrypoint for substantive UI work
3. require an explicit `ui surface` declaration before loading more frontend skills
4. record the entrypoint in task artifacts so review and tests can verify the routing decision

## Detailed backlog

Completed in this slice:

1. Make the shipped frontend entrypoint explicit in `devgod-ui-art-direction`.
2. Require `ui surface` declaration and frontend-entrypoint recording in the task packet and acceptance/rubric files.
3. Teach the shipped `frontend_designer` and `planner` Codex roles to route UI work through the entrypoint and skip the wider cluster on non-UI tasks.
4. Add control-layer test coverage for the new Codex routing contract.

Still desirable but out of this task's allowed write scope:

1. Add a dedicated thin wrapper skill such as `devgod-frontend` that mirrors `archon-frontend` and points into `devgod-ui-art-direction`, `devgod-frontend-taste`, and `devgod-design-system`.
2. Update any repo-local agent catalog or maintainer docs outside this scope so the frontend hub appears in the canonical role matrix, not only in prompts.
3. Add install and drift tests that prove non-UI tasks do not pull the frontend cluster and that UI tasks do.
4. Extend the same entrypoint pattern to adjacent visual roles such as `ux_researcher` and any future mobile-specialist role.

## New diagnosis: literal-vibe collapse

The latest `hexchange` passes exposed another workflow failure: even after the anti-anchoring upgrade, the agent still interpreted an avatar-style reference too literally.

The surface got closer in palette and illustration style, but it still missed the real ask because it treated the reference as:

- a hero-art cue
- a decoration source
- a moodboard for static panels

instead of as:

- a motion personality
- a charm vocabulary
- a material system
- an interaction tone for the whole product

That produced a familiar failure pattern:

- the "cute magical dev workstation" feeling stayed trapped inside one art panel
- the rest of the product remained disciplined but ordinary utility surfaces
- whimsical details appeared as isolated props rather than as a coherent living interface language
- the agent answered "where do I put witchy things?" instead of "how should the whole interface behave if it lived in this world?"

## What stronger systems imply here

The public workflow evidence points in the same direction:

- v0's screenshot-and-versions guidance treats reference images as spatial and aesthetic steering, not as direct content to paste into the result
- Replit Agent 4's creativity framing emphasizes multiple variants and in-context exploration, which is exactly what is needed to reinterpret a vibe source rather than freezing on the first literal reading
- Lovable's visual edits model reinforces that visual correction should happen on details like layout, imagery, text, and style relationships, not only on whole-page rewrites

My inference from those sources is that `devgod` needs one more explicit contract:

- every image-led redesign must produce a reference translation brief before implementation
- every playful redesign must produce a semantic charm map before implementation
- the default question becomes "what recurring rules does this reference teach us?" rather than "where can this picture show up?"

## New default behavior

For autonomous frontend agents, a supplied avatar, illustration, or vibe image now needs to be translated into:

- motion personality
- palette energy
- line and corner softness
- glow behavior
- charm vocabulary
- idle-state aliveness
- interaction tone
- material logic

Only after that translation exists should the agent choose whether any literal illustration belongs in the product at all.

This is the contract that should make future outputs less likely to over-focus on a constructed hero module and more likely to distribute the desired feeling across the full UI.

- the planner must classify whether the task is an edit or a remake
- remake tasks must name an inheritance cutoff and a legacy carryover ban before coding
- at least one variant must be blank-slate and structurally independent from the current surface
- the final browser critique must include an inheritance audit, not just a polish audit
- if the result still shares the old shell rhythm or mixes old and new languages, it fails even if it looks more polished


## New diagnosis: same primitives, new order

The latest failure mode is stricter than ordinary legacy anchoring. Even after the anti-anchoring and vibe-translation upgrades, the workflow still let one family of primitives survive:

- dark shell containers
- giant serif headline slabs
- metric-card strips
- utility panel stacks
- minor atmospheric motion used as garnish

That means the workflow was still changing arrangement more than medium. The result could look somewhat different at first glance, but it still behaved like the same product family with a new order.

## What current source evidence adds

The stronger systems now point to a sharper conclusion:

- Anthropic's Claude Code UI guidance treats screenshots as critique input and encourages building feedback loops around what the rendered interface actually looks like, not just around the source code. [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)
- Vercel's v0 guidance emphasizes screenshots, sketches, versions, and rollback-style iteration because text alone is not enough to describe strong visual intent. [Vercel Academy, Screenshots and Versions](https://vercel.com/academy/v0-foundations/enhance-design-with-screenshots-and-versions)
- Replit Agent 4 frames creativity around a canvas, multiple options, and contextual exploration instead of one-shot layout editing. [Replit Agent 4](https://replit.com/blog/introducing-agent-4-built-for-creativity)
- Lovable's design workflow explicitly includes visual edits, image replacement, and generated image support, which means stronger systems do not treat authored media as an afterthought. [Lovable Design](https://docs.lovable.dev/features/design-guidance), [Lovable image generation](https://docs.lovable.dev/features/ai-image-generation)
- OpenAI's image-generation guidance supports using images as inputs and generating edited outputs, which reinforces the idea that reference-led UI work can produce bespoke assets instead of relying on placeholder decoration. [OpenAI image generation guide](https://platform.openai.com/docs/guides/image-generation)
- `Rive`, `Motion`, `GSAP`, and `three.js` together show that modern immersive UI has multiple legitimate media paths, but each one needs an explicit fit decision rather than being silently skipped. [Rive runtimes](https://rive.app/docs/runtimes), [Motion for React](https://motion.dev/docs/react), [GSAP ScrollTrigger](https://gsap.com/docs/v3/Plugins/ScrollTrigger/), [three.js scene guide](https://threejs.org/manual/en/creating-a-scene.html)

My inference from these sources is that `devgod` needed one more contract layer: not only "be original" and "translate the vibe image," but also "choose the authored medium that will actually carry the experience."

## New default behavior: media-first family reset

Broad remakes should now answer these questions before implementation:

- what design family is being replaced?
- which repeated primitives are banned from surviving?
- what authored medium will carry the new family?
- should generated imagery, edited artwork, sprite work, authored interaction art, or 3D depth be part of the concept?
- if those media are not used, why is a lighter path actually stronger for this task?

Without those answers, the workflow can still drift into the same shell family with better polish. With them, the agent has to change the underlying grammar of the interface, not only its mood.

## New diagnosis: code-first variant collapse

The next plateau showed up after the workflow had already learned stronger language about references, family resets, and media choices: the agent still kept doing too much exploration directly inside production code.

That creates a new failure pattern:

- the route code becomes the first design canvas
- "variants" are really code edits on top of the same shell
- the cost of radical divergence feels too high once the production structure exists
- each revision becomes a negotiation with inherited markup instead of a proof of a new family

This is where the latest public evidence becomes especially useful:

- Vercel's current v0 guidance encourages screenshots, sketches, interpretation rather than copying, and version rollback for experimentation. [Vercel Academy, Screenshots and Versions](https://vercel.com/academy/v0-foundations/enhance-design-with-screenshots-and-versions)
- Replit's current Canvas workflow explicitly separates mockups from the running app, supports multiple directions side by side, and only later applies the chosen direction back into the app. [Replit Canvas](https://docs.replit.com/learn/projects-and-artifacts/canvas), [Design with Canvas](https://docs.replit.com/getting-started/quickstarts/design-with-canvas)
- Lovable's current design guidance shows three directions before the full build and then lets users refine them before submission. [Lovable Design Guidance](https://docs.lovable.dev/features/design-guidance)
- Lovable's visual edits feature reinforces that precise visual correction can happen directly on the rendered surface without immediately rewriting the whole product. [Lovable Visual Edits](https://docs.lovable.dev/features/design)

My inference from those sources is that `devgod` needed another control:

- broad remakes must create at least one externalized visual exploration artifact before production code starts
- acceptable artifacts include a lightweight HTML mock, SVG storyboard, screenshot paintover, generated image, or equivalent durable visual concept artifact
- if the first critique still reads as "same family reordered," the agent must produce one explicit `opposite-direction artifact` before continuing implementation

## Dashboard exception

One more workflow trap appeared in the evidence: commodity tools often skip design-guidance flows for dashboards, admin panels, internal tools, or games because those surfaces are assumed to be more functional than expressive.

That shortcut is useful for generic productivity tooling, but it is the wrong default for `devgod`'s stated goal. The current proof target, `hexchange`, is exactly the kind of dense control-bearing surface that still needs authored direction when the goal is exceptional frontend work.

So the upgraded `devgod` contract should say the opposite:

- dashboard, control-center, admin, and game-like surfaces do not get to skip the exploration-artifact step
- if a utility-bearing surface is the target, the workflow must prove that strong visual authorship and control discoverability can coexist before implementation hardens
